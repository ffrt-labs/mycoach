# Single Postgres instance, two schemas, not two databases

The eventual destination is a separate health-data application, and this leg could have rehearsed that more literally by provisioning two separate database instances now, one per future application. Instead, health and coaching live in one Postgres instance, in separate schemas behind separate owner and runtime roles — `coaching_role` holds no grant at all on `health`, not even `USAGE`, so a cross-schema query fails with a permission error rather than passing review — with two independent Alembic histories, one per schema. A single instance keeps homelab operational overhead down (one thing to back up, monitor, and run), while the schema/role wall already gives the property that matters for validating the boundary before physically splitting: nothing in the code can depend on cross-boundary access working. Moving each schema to its own instance later is expected to be comparatively mechanical, since that dependency was never allowed to exist.
