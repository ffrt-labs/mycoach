# Durable events modelled as vocabulary now, transport later

The physical split will eventually need a message broker so the health side can durably notify coaching, but that layer isn't warranted for a single-process, single-instance first leg — coaching could simply call a function. Instead, `CanonicalActivityRecorded`, `CanonicalActivitySettled`, and `CanonicalActivityRevised` are modelled as typed events with deterministic (not random) IDs and idempotent handlers, raised in-process and dispatched by the calling code only after the health-side transaction commits, with no broker or pub/sub registry yet. `CanonicalActivitySettled` in particular encodes a real timing decision — is it safe to generate final post-workout coaching yet? — that exists independent of transport; skipping the vocabulary would just push that logic into ad-hoc conditionals that would need rediscovering later. Modelling it as an event now means the eventual swap to a real broker only changes how the event reaches its handler, not its shape or the discipline around it. The accepted consequence: with no redelivery mechanism yet, a failed handler is a genuine gap until the broker exists, mitigated only by handlers being safe to re-invoke by hand once a failure is noticed in logs.
