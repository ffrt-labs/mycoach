PROTOTYPE — Health module boundary (throwaway, do not ship)

Question: #111 asks what the health module's interface should look like — the in-process boundary that will later become the Health-data API over HTTP. The operations must be right now because the physical split only swaps the implementation, not the callers.

This demo simulates two separate stores — health (canonical activities, exercise catalogue) and coaching (planned sessions, prescription fulfillments) — that can only talk through the boundary functions below, using each other's external IDs, never an internal database id. That's the constraint #85 already decided (“neither uses a cross-database foreign key”); this demo is where it gets tested against real call shapes instead of argued on paper.

Press buttons freely, or run a guided walkthrough below. Watch for the moment something you expected to work doesn't — that's the interface telling you something.
